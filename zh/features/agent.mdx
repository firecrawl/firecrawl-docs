Firecrawl `/agent` 是一个魔法般的 API，它可以在最广泛的网站范围内进行搜索、导航并收集数据，在难以触及的角落中找到数据，并以其他任何 API 都无法做到的方式发掘信息。它可以在几分钟内完成原本需要人类耗费数小时的工作——从端到端的数据采集，全程无需脚本或人工操作。
无论你只需要一个数据点，还是需要大规模的完整数据集，Firecrawl `/agent` 都能为你获取这些数据。

**把 `/agent` 想象成：无论数据藏在哪里，它都能替你做深度调研！**

代理构建于 `/extract` 的全部优势之上，并在此基础上更进一步：

* **无需提供 URL**：只需通过 `prompt` 参数描述你的需求，URL 是可选的。
* **深度网页搜索**：自主搜索并深入浏览站点以找到所需数据
* **可靠且准确**：适用于多种类型的查询和使用场景
* **更快**：并行处理多个数据源以更快返回结果

## 任务状态与完成 {#job-status-and-completion}

代理任务以异步方式运行。提交任务后，你会收到一个 Job ID，用于检查任务状态：

* **默认方式**：`agent()` 会阻塞等待，并返回最终结果
* **先启动再轮询**：使用 `start_agent` (Python) 或 `startAgent` (Node) 立即获取 Job ID，然后通过 `get_agent_status` / `getAgentStatus` 进行轮询
* **推送而非轮询**：启动任务时传入 `webhook`，即可在运行过程中及完成时接收[代理事件](/zh/webhooks/events#agent-events)

<Note>任务结果在完成后可通过 API 获取，保留 24 小时。在此之后，你仍然可以在 [activity logs](https://www.firecrawl.dev/app/logs) 中查看你的代理历史记录和结果。</Note>

### 可能的状态 {#possible-states}

| 状态           | 描述                                                                                                                      |
| ------------ | ----------------------------------------------------------------------------------------------------------------------- |
| `processing` | 代理仍在处理你的请求                                                                                                              |
| `completed`  | 提取已成功完成                                                                                                                 |
| `failed`     | 提取过程中发生错误、运行达到 `maxCredits` 上限 (请参见[处理因额度上限而停止的情况](#handling-credit-limit-stops))，或任务被取消 (被取消的任务会报告 `failed`，并附带取消错误消息) |

</Note>

## 处理因额度上限而停止的情况 {#handling-credit-limit-stops}

运行 达到 `maxCredits` 上限时会停止，并报告 `status: "failed"`。要区分因额度耗尽而停止与其他失败，请检查 `stopReason`，而不是 `error` 文本。运行 用尽预算时，`stopReason` 为 `credit_limit_reached`。

`data` 仅在已完成的 运行 中设置，失败的 运行 中不会有。因额度耗尽而失败的 运行 可能会包含代理在停止前已收集到的内容：

| 字段                   | 类型      | 描述                                                 |
| -------------------- | ------- | -------------------------------------------------- |
| `stopReason`         | string  | 运行 提前停止的原因。目前仅有 `credit_limit_reached`。           |
| `partial`            | any     | 从未完成的 运行 中尽力恢复的 JSON，可能缺少部分行或字段。                  |
| `partialSchemaValid` | boolean | 仅当请求中包含 `schema` 时出现，表示 `partial` 是否通过该 schema 校验。 |
| `message`            | string  | 简要说明哪些内容不完整 (如有) 。                                 |

这些字段仅在 运行 失败后才会出现。运行 处于 `processing` 状态时，状态响应中不会包含部分结果。

<Warning>
  请谨慎使用 `partial`。它并不完整，因此不要将其作为最终结果存储；用你的 schema 解析之前，请先检查 `partialSchemaValid`。并非每次因额度耗尽而停止都会返回 `partial`，因此也要处理只返回 `stopReason` 的 运行。
</Warning>

要完成剩余工作，请在该 运行 的会话中发送后续 prompt。之前的 `partial` 会为代理恢复并标记为不完整，因此后续请求会在此基础上继续，而不必从头开始。后续请求会继承上一轮的 `schema` 和 `urls`，但不会继承 `maxCredits`，因此请为其单独设置预算。

## 跟踪正在进行的运行 {#following-a-run-in-progress}

代理不会维持流式连接。既没有服务器发送事件流，也没有 WebSocket，因此你可以通过轮询执行追踪或接收 Webhook 来跟踪运行。

| 工具集     | 可获取内容                                                                                                                                            | 最适合                       |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------- |
| 执行追踪轮询  | 完整详情：截至目前运行发出的所有事件，包括工具调用、推理摘要、进度阶段和工件变更                                                                                                         | 构建自定义进度 UI，或调试运行实际执行了什么操作 |
| Webhook | 推送交付，粒度较粗：五个代理生命周期事件 (`agent.started`、`agent.action`、`agent.completed`、`agent.failed`、`agent.cancelled`) 。请参见 [webhook events](/zh/webhooks/events) | 无需持续运行轮询循环即可响应运行完成        |
| 实时视图    | 可供人工查看的代理浏览器视图。请求执行追踪时添加 `?liveView=true`，`activeBrowserSessions` 中的每个条目都会包含 `liveViewUrl`                                                       | 实时观察运行的导航过程               |

如果要自行排序执行追踪事件，请先按 `agent.id` 分组：`producerSequence` 对每个发出事件的代理而言都是单调递增的，因此全局排序会错误地交错编排器及其子代理的事件。终止事件 `run.finished` 发出后，事件仍可能在短时间内到达，因此在渲染最终状态前，请在短暂的尾部窗口内继续轮询。

## 获取代理的源数据 {#getting-the-agents-source-data}

运行会在执行过程中持续将工作输出写入工件。获取该运行的执行追踪后，即可检索这些工件。每个 `artifact.updated` 事件描述某个工件的一次变更：`artifact.kind` 可以是 `json`、`markdown`、`html`、`screenshot` 或 `text`，`artifact.path` 表示运行将其写入的位置，而 `artifact.snapshotId` 则是用于通过 `GET /agent/{jobId}/snapshots/{snapshotId}` 获取其内容的句柄。快照端点会在 `snapshot` 字段中以字符串形式返回该内容：对于 `json` 工件，该字符串经过 JSON 编码，需要解码；而 `markdown`、`html` 和 `text` 工件则直接返回内容本身。

要获取运行生成的页面内容，请先获取执行追踪，保留所需 `kind` 的 `artifact.updated` 事件，然后获取每个快照：

<CodeGroup>
  <AgentArtifactsPython />

  <AgentArtifactsJS />

  <AgentArtifactsCURL />
</CodeGroup>

在此基础上进行开发前，有两点需要了解：

* **工件是运行的输出，并非逐页存档。** 运行写入工件的内容取决于它如何处理你的 prompt，因此应将工件集视为该次运行生成的内容，而不是其打开的每个页面的完整记录。
* **其余内容位于工具结果中。** 每个 `tool_call.finished` 事件都包含一个 `result` 字段，其中保存该工具返回的内容；未成为工件的内容会出现在这里。

## 模型选择 {#model-selection}

Firecrawl 代理使用 **Spark 2**，相比早期的 Spark 1 模型成本更低、速度更快，准确率相当。它是默认值：无论是否设置 `model` 参数，每次运行都会使用 `spark-2`。

<Note>
  **Spark 1 模型已弃用。** 为保持向后兼容，仍接受 Spark 1 模型名称，但使用这些名称的请求会被路由到 `spark-2`。
</Note>

### Spark 2 {#spark-2}

`spark-2` 覆盖了此前需要在 Mini 和 Pro 之间取舍的全部任务，因此无需再权衡准确率与成本。

**亮点：**

* 单次运行成本最低
* 运行时间最快
* 准确率可媲美之前的 Spark 1 旗舰模型
* 唯一支持推理预算的模型：传入 `effort` (`low`、`medium` 或 `high`) 以控制其思考深度

## 需要接受条款的数据提供商 {#data-providers-that-need-terms}

代理在运行期间可以调用 [Alexandria](/zh/features/alexandria) 数据提供商，但仅限于你的团队已接受其数据条款的提供商。对于尚未接受条款的提供商，无论 `exchange.onTermsRequired` 如何设置，都不会被调用。运行会继续使用可用的提供商，状态响应中会列出被跳过的提供商。

不支持自动接受模式。接受提供商的条款必须由人来确认：可以在 [Dashboard](https://www.firecrawl.dev/app/settings?tab=data-sources) 中操作，也可以由你的应用在用户明确同意后调用 `terms/accept`。如果你基于 Firecrawl 构建代理，该代理必须先征得用户同意，再调用 `terms/accept`。请求数据并不代表同意提供商的条款。

| `onTermsRequired` | 行为                                                                                                               |
| ----------------- | ---------------------------------------------------------------------------------------------------------------- |
| `skip` (默认值)      | 运行仅使用已接受条款的提供商作答，且不会阻塞。`exchange.skippedProviders` 会列出本可派上用场、但受条款限制的提供商。                                         |
| `ask`             | 与 `skip` 相同。此外，运行结束时会返回 `exchange.requiresAction` 以及一个 `kind: "terms"` 的 `pendingApproval`，便于你征询用户、接受条款，然后继续该会话。 |

如果在会话的后续轮次中省略 `onTermsRequired`，该轮次将沿用上一轮的值。如果某一轮次因需要审批付费调用 (`requireApproval`) 而结束，则该轮次不会提示接受条款。

### 响应字段 {#response-fields}

以下字段位于 `GET /v2/agent/{id}` 的 `exchange` 对象中：

* `skippedProviders` (任意模式) ：每个本可派上用场、但因条款限制而被跳过的提供商对应一个条目，包含 `provider`、`name`、`capability`、`adds` (本可补充的内容) 、`reason: "terms_required"`、`version` (条款版本) 和 `termsUrl` (在 Dashboard 中接受条款的位置) 。
* `requiresAction` (仅限 `ask`) ：包含 `type: "accept_terms"`、一个 `approvalId` 和一个 `providers` 列表。`approvalId` 始终存在，它是 `terms` 待审批项的 id，你在继续该会话时需要对其作出答复。每个提供商都附带需要执行的具体 `show` (`terms/show`) 和 `accept` (`terms/accept`) 调用。每个提供商的 `digest` (以及 `accept.options.digest`) 字段始终存在，但值可能为 `null`，表示目录未发布摘要。遇到这种情况，请先运行 `terms/show`，再发送其返回的摘要。

      {

### 先接受条款，再继续 {#accept-then-continue}

在 `ask` 模式下：

1. 向用户展示条款。通过 [`/v2/scrape`](/zh/features/alexandria) 并使用 `alexandria` 执行该提供商的 `show` 调用。
2. 仅在用户明确同意后，才以相同方式执行其 `accept` 调用。如果 `accept.options.digest` 为 `null`，请使用 `terms/show` 返回的 digest：

```bash
curl -X POST https://api.firecrawl.dev/v2/scrape \
  -H "Authorization: Bearer $FIRECRAWL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "alexandria": {
      "provider": "firecrawl",
      "capability": "terms/accept",
      "options": { "provider": "apollo", "version": "F-1.0.0", "digest": "<sha256>", "confirmed": true }
    }
  }'
```

3. 使用 `exchange.approve` 在同一会话中继续。该提议会被整体接受，其中的 `callIds` 和 `always` 将被忽略。下一轮会调用这些提供商来补足上一个答案中指出的缺口，而不会重新运行全部内容。

```bash
curl -X POST https://api.firecrawl.dev/v2/agent \
  -H "Authorization: Bearer $FIRECRAWL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "threadId": "<threadId from the previous run>",
    "prompt": "Continue with Apollo.",
    "exchange": {
      "approve": { "approvalId": "0199aaaa-0000-7000-8000-000000000000" }
    }
  }'
```

如果想在不使用该提供商的情况下继续，请改用 `exchange.decline: { "approvalId": "..." }` 继续。这会拒绝整个报价，且在该会话的后续过程中，其中的提供商都不会再被提供。

在 `skip` 模式下，没有需要回复的待审批项。接受条款后，发起一次新的运行 (或在该会话中开始新一轮对话) ，即可使用该提供商。

## 价格 {#pricing}

Firecrawl Agent 使用 **动态计费** 模式，费用会随你的数据提取请求复杂度而变化。你根据 Agent 实际完成的工作量付费，无论是提取简单的数据点，还是从多个来源获取复杂的结构化信息，都能享受公平的定价。

### 代理 计费方式 {#how-agent-pricing-works}

代理 的计费是**动态的、基于 额度 的**：

* **简单提取任务** (例如从单个页面提取联系方式) 通常消耗更少的 额度，成本更低
* **复杂研究任务** (例如对多个域名进行竞品分析) 会消耗更多 额度，但更能体现整体投入的工作量
* **用量透明**会清楚展示每个请求具体消耗了多少 额度
* **额度 换算**会自动将 代理 的 额度 使用量换算为 额度，便于计费

<Info>
  额度 使用量会因 prompt 的复杂度、处理的数据量以及期望输出的结构而有所不同。大致来说，大多数 代理 运行会消耗**数百个 额度**，更简单的单页任务可能会用得更少，而复杂的多域名研究可能会用得更多。
</Info>

### 并行代理计费 {#parallel-agents-pricing}

如果你使用 Spark-2 Fast 并行运行多个代理，费用会更加可预测：每个 cell 消耗 10 个额度。

### 入门 {#getting-started}

**所有用户**每天都会获得**5 次免费运行**，可以通过 playground 或 API 使用，用于在无需付费的情况下体验 Agent 的功能。

额外用量会根据 credit 消耗计费，并换算为 credits。

### 成本管理 {#managing-costs}

代理可能会比较昂贵，但有一些方法可以降低成本：

* **从免费运行开始**：利用你每天 5 次免费请求来了解定价
* **设置 `maxCredits` 参数**：通过设置你愿意花费的最大额度数来限制支出。Dashboard 将此上限设为 2,500 额度；若要设置更高的上限，请直接通过 API 使用 `maxCredits` 参数 (注意：高于 2,500 的值始终按付费请求计费)
* **优化 prompt**：更具体的 prompt 通常会消耗更少的额度
* **将大型任务拆分为更小的运行**：单次代理运行大约会返回 150-200 行结构化数据。对于大型提取任务，可按类别、地区或 URL 批次 (每次运行 3-5 个 URL) 进行拆分，再合并结果。这也能让每次运行都保持在 `maxCredits` 限制之下。
* **监控用量**：通过 Dashboard 追踪你的使用情况
* **设定预期**：跨多个域名的复杂研究会比简单的单页提取消耗更多额度

现在访问 [firecrawl.dev/app/agent](https://www.firecrawl.dev/app/agent) 试用代理，看看在你的具体用例下额度的使用如何随规模变化。
