**Escolhendo a ferramenta certa.** agente é a escolha certa quando você **não sabe quais são as URLs** ou precisa de navegação autônoma pela web.

<ChooseDataExtractor />

Firecrawl `/agent` é uma API mágica que pesquisa, navega e coleta dados da mais ampla variedade de sites, encontrando dados em locais de difícil acesso e descobrindo dados de maneiras que nenhuma outra API consegue. Ele realiza em poucos minutos o que levaria muitas horas para um humano — coleta de dados de ponta a ponta, sem scripts ou trabalho manual.
Seja para obter um único dado ou conjuntos de dados completos em escala, o Firecrawl `/agent` trabalha para obter seus dados.

**Pense no `/agent` como uma pesquisa profunda por dados, onde quer que eles estejam!**

agente aproveita tudo o que há de melhor no `/extract` e leva isso além:

* **Sem necessidade de URLs**: basta descrever o que você precisa no parâmetro `prompt`. As URLs são opcionais
* **Busca profunda na web**: busca e navega de forma autônoma até as camadas mais profundas dos sites para encontrar seus dados
* **Confiável e preciso**: funciona com uma grande variedade de queries e casos de uso
* **Mais rápido**: processa várias fontes em paralelo para entregar resultados mais rapidamente

## Status e conclusão de jobs {#job-status-and-completion}

Jobs de agente são executados de forma assíncrona. Ao enviar um job, você recebe um Job ID que pode usar para verificar o status:

* **Método padrão**: `agent()` aguarda e retorna os resultados finais
* **Iniciar e depois consultar**: use `start_agent` (Python) ou `startAgent` (Node) para obter um Job ID imediatamente e depois verificar o status com `get_agent_status` / `getAgentStatus`
* **Notificação em vez de consulta**: passe um `webhook` ao iniciar o job para receber [eventos do agente](/pt-BR/webhooks/events#agent-events) conforme a execução avança e é concluída

<Note>Os resultados do job ficam disponíveis via API por 24 horas após a conclusão. Após esse período, você ainda pode ver o histórico do seu agente e os resultados nos [logs de atividade](https://www.firecrawl.dev/app/logs).</Note>

| Status       | Descrição                                                                                                                                                                                                                                                                  |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `processing` | O agente ainda está trabalhando na sua requisição                                                                                                                                                                                                                          |

Os créditos podem continuar sendo consumidos durante esse breve intervalo, então o `creditsUsed` final pode ser maior do que o valor informado no momento em que você clicou em cancelar. Um job cancelado informa o status `failed` quando consultado e emite um evento de webhook `agent.cancelled`.
</Note>

## Como lidar com interrupções por limite de créditos {#handling-credit-limit-stops}

Uma execução que atinge o limite definido em `maxCredits` é interrompida e retorna `status: "failed"`. Para distinguir uma interrupção por créditos de outras falhas, verifique `stopReason` em vez do texto de `error`. `stopReason` é `credit_limit_reached` quando a execução esgota o orçamento.

`data` só é preenchido em execuções concluídas, nunca em execuções com falha. Uma execução que falhou por falta de créditos pode incluir o que o agente já havia coletado antes de parar:

| Campo                | Tipo    | Descrição                                                                                                |
| -------------------- | ------- | -------------------------------------------------------------------------------------------------------- |
| `stopReason`         | string  | Motivo pelo qual a execução parou antes do previsto. Atualmente, apenas `credit_limit_reached`.          |
| `partial`            | any     | JSON recuperado da execução incompleta, na medida do possível. Pode ter linhas ou campos faltando.       |
| `partialSchemaValid` | boolean | Presente apenas quando a requisição incluiu um `schema`. Indica se `partial` é válido de acordo com ele. |
| `message`            | string  | Uma breve observação sobre o que ficou incompleto, quando disponível.                                    |

Esses campos só aparecem depois que a execução falha. Enquanto a execução está em `processing`, a resposta de status nunca inclui um resultado parcial.

<Warning>
  Use `partial` com cuidado. Como ele está incompleto, não o armazene como resultado final e verifique `partialSchemaValid` antes de processá-lo com seu schema. Nem toda interrupção por créditos retorna um `partial`, então trate também as execuções que retornam apenas `stopReason`.
</Warning>

Para concluir o trabalho, continue a thread da execução com um novo prompt. O `partial` anterior é restaurado para o agente e marcado como incompleto, de modo que a continuação parte dele em vez de recomeçar do zero. A continuação herda o `schema` e as `urls` do turno anterior, mas não o `maxCredits`, então defina um orçamento para ela.

## Listando execuções de agentes {#listing-agent-runs}

`GET /agent` lista todas as execuções de agentes da sua equipe, das mais recentes às mais antigas — incluindo as iniciadas no playground ou pela API. Cada entrada inclui o ID da execução, a hora de criação, o status, uma breve indicação do destino e as opções com que ela foi iniciada.

Os resultados são paginados em páginas fixas de 20 execuções. Quando houver mais páginas, a resposta incluirá uma URL `next`; use o timestamp `before` dela para buscar a próxima página. Os métodos do SDK não paginam automaticamente, para que você mantenha o controle de até onde voltar.

O agente não mantém uma conexão de streaming aberta. Não há stream de eventos enviados pelo servidor nem websocket, então acompanhe uma execução consultando seu rastro ou recebendo webhooks.

| Webhooks                   | Entrega por push, em nível mais amplo: os cinco eventos do ciclo de vida do agente (`agent.started`, `agent.action`, `agent.completed`, `agent.failed`, `agent.cancelled`). Consulte [eventos de webhook](/pt-BR/webhooks/events) | Reagir ao término de uma execução sem manter um loop de consulta aberto       |

## Obtendo os dados de origem do agente {#getting-the-agents-source-data}

Uma execução grava seus resultados parciais em artefatos à medida que avança, e você pode recuperá-los depois de obter o rastro da execução. Cada evento `artifact.updated` descreve uma alteração em um artefato: `artifact.kind` pode ser `json`, `markdown`, `html`, `screenshot` ou `text`; `artifact.path` indica onde a execução o salvou; e `artifact.snapshotId` é o identificador que você usa para obter seu conteúdo em `GET /agent/{jobId}/snapshots/{snapshotId}`. O endpoint de snapshots retorna esse conteúdo em um campo `snapshot` como uma string: para artefatos `json`, essa string é codificada em JSON e precisa ser decodificada, enquanto, para artefatos `markdown`, `html` e `text`, ela é o próprio conteúdo.

Para obter o conteúdo de página produzido por uma execução, busque o rastro, filtre os eventos `artifact.updated` pelo `kind` desejado e, em seguida, busque cada snapshot:

<CodeGroup>
  <AgentArtifactsPython />

  <AgentArtifactsJS />

  <AgentArtifactsCURL />
</CodeGroup>

Duas coisas importantes antes de usar isso como base:

* **Os artefatos são o resultado da execução, não um arquivo de cada página.** O que uma execução grava em um artefato depende de como ela processa seu prompt. Portanto, trate o conjunto de artefatos como o que aquela execução específica produziu, e não como um registro garantido de todas as páginas que ela abriu.
* **Os resultados das ferramentas contêm o restante.** Cada evento `tool_call.finished` inclui um campo `result` com o que a ferramenta retornou. É nele que aparece o conteúdo que nunca se tornou um artefato.

## Seleção de modelo {#model-selection}

O Firecrawl Agent é executado no **Spark 2** — mais barato e mais rápido que os modelos Spark 1 anteriores, com precisão comparável. Ele é o modelo padrão: todas as execuções usam `spark-2`, independentemente de você definir o parâmetro `model`.

<Note>
  **Os modelos Spark 1 estão descontinuados.** Os nomes dos modelos Spark 1 continuam aceitos por compatibilidade retroativa, mas as solicitações que os utilizam são direcionadas para `spark-2`.
</Note>

### Spark 2 {#spark-2}

`spark-2` abrange toda a gama de tarefas que antes exigiam escolher entre Mini e Pro, eliminando a necessidade de abrir mão da precisão para reduzir custos.

**Destaques:**

* Menor custo por execução
* Tempo de execução mais rápido
* Precisão comparável ao antigo carro-chefe Spark 1
* O único modelo com um orçamento de raciocínio: passe `effort` (`low`, `medium` ou `high`) para controlar o quanto ele raciocina

## Use suas ferramentas conectadas do Alexandria {#use-your-connected-alexandria-tools}

O agente pode chamar os providers de dados do [Alexandria](/pt-BR/features/alexandria) da sua equipe durante uma execução, além da web. No [playground](https://www.firecrawl.dev/app/agent), eles já vêm ativados. Pela API e pelos SDKs, uma execução usa apenas a web até que você envie um object `exchange`; portanto, uma requisição sem ele nunca usa seus providers.

Envie `exchange` com `enabled: true` para permitir que o agente use todos os providers disponíveis para sua equipe, ou fixe até cinco com `toolkits`:

<CodeGroup>
  <AgentAlexandriaPython />

  <AgentAlexandriaJS />

  <AgentAlexandriaCURL />
</CodeGroup>

| Campo                | O que faz                                                                                                                                                                                        |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `enabled`            | Permite que o agente chame providers. O padrão é `true` assim que você envia `exchange`, então um object vazio também os ativa. Envie `false` para desativá-los em um único turno de uma thread. |
| `toolkits`           | Até 5 slugs de providers, como `["apollo"]`. O agente usa apenas esses. Se vazio ou omitido, o agente usa todos os providers disponíveis para sua equipe.                                        |
| `maxCalls`           | Número máximo de chamadas a providers que o agente pode fazer em um turno, de 1 a 30. O padrão é 16.                                                                                             |
| `requireApproval`    | Interrompe o turno antes de qualquer chamada paga a um provider e o encerra com um `pendingApproval` para você responder. Exige `mode: "chat"` na mesma requisição. O padrão é `false`.          |
| `approve`, `decline` | Respondem ao `pendingApproval` do turno anterior no próximo turno da thread. Veja [Aprovar chamadas pagas antes de serem executadas](#approve-paid-calls-before-they-run).                       |
| `onTermsRequired`    | O que fazer quando um provider exige termos de dados que sua equipe ainda não aceitou. Veja [Providers de dados que exigem termos](#data-providers-that-need-terms).                             |

O object `exchange` da resposta de status informa o que a execução fez: `enabled`, os `toolkits` e o `requireApproval` usados na execução, `paidCalls` (chamadas pagas a providers realizadas) e `creditsUsed` (quanto essas chamadas custaram, ou `null` quando nenhuma foi registrada).

### Turnos subsequentes {#follow-up-turns}

Um turno subsequente de uma thread (uma requisição com `threadId`) que omite `exchange` mantém a configuração do turno anterior. Se ele enviar um object `exchange`, `toolkits` e `onTermsRequired` continuam sendo herdados quando omitidos, mas `enabled`, `maxCalls` e `requireApproval` voltam aos valores padrão, a menos que você os envie novamente.

### Aprove chamadas pagas antes da execução {#approve-paid-calls-before-they-run}

Com `requireApproval: true`, o agente para antes da primeira chamada paga a um provider, e o turno termina com um `pendingApproval` do tipo `kind: "calls"`. Ele contém um `id`, o `reason` do agente e as `calls` que ele pretende fazer, cada uma com `id`, `provider`, `capability`, `input` e `creditsEstimate`. Mostre essas chamadas ao usuário e responda no turno seguinte da mesma thread:

* `exchange.approve: { "approvalId": "<pendingApproval.id>" }` executa as chamadas. Adicione `callIds` para executar apenas algumas delas ou `always: true` para não pedir mais aprovação até o fim da thread.
* `exchange.decline: { "approvalId": "<pendingApproval.id>" }` ignora as chamadas, e o agente responde sem elas.

Envie `requireApproval: true` novamente no turno de resposta para que as próximas chamadas pagas continuem aguardando aprovação. Os dois turnos exigem `mode: "chat"`.

## Providers de dados que exigem aceite de termos {#data-providers-that-need-terms}

Quando uma execução usa providers de dados do [Alexandria](/pt-BR/features/alexandria), ela chama apenas aqueles cujos termos de dados sua equipe já aceitou. Um provider cujos termos você não aceitou nunca é chamado, independentemente do valor de `exchange.onTermsRequired`. A execução continua com os providers que pode usar, e a resposta de status informa o que foi ignorado.

Não existe modo de aceite automático. Aceitar os termos de um provider sempre exige que uma pessoa concorde com eles, seja no [painel](https://www.firecrawl.dev/app/settings?tab=data-sources) ou por meio de uma chamada `terms/accept` feita pela sua aplicação depois que o usuário tiver concordado explicitamente. Se você criar um agente com base no Firecrawl, ele deve pedir a confirmação do usuário antes de chamar `terms/accept`. Uma solicitação de dados não equivale a consentimento com os termos de um provider.

| `onTermsRequired` | O que acontece                                                                                                                                                                                            |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `skip` (padrão)   | A execução responde apenas com providers aceitos e nunca fica bloqueada. `exchange.skippedProviders` lista os providers restritos que teriam ajudado.                                                     |
| `ask`             | Igual a `skip`. Além disso, a execução termina com `exchange.requiresAction` e um `pendingApproval` com `kind: "terms"`, para que você possa consultar o usuário, aceitar os termos e continuar a thread. |

Se você omitir `onTermsRequired` em um turno seguinte de uma thread, o turno usará o valor do turno anterior. Se um turno terminar em uma aprovação de chamada paga (`requireApproval`), ele não inclui oferta de termos.

### Campos da resposta {#response-fields}

Estes campos ficam no objeto `exchange` de `GET /v2/agent/{id}`:

* `skippedProviders` (qualquer modo): uma entrada para cada provider restrito que teria ajudado, com `provider`, `name`, `capability`, `adds` (o que ele teria acrescentado), `reason: "terms_required"`, `version` (a versão dos termos) e `termsUrl` (onde aceitar os termos no painel).
* `requiresAction` (somente `ask`): `type: "accept_terms"`, um `approvalId` e uma lista `providers`. O `approvalId` está sempre presente. Ele é o id da aprovação pendente de `terms` que você responde ao dar continuidade à thread. Cada provider traz as chamadas exatas de `show` (`terms/show`) e `accept` (`terms/accept`) que devem ser feitas. O `digest` de cada provider (e `accept.options.digest`) está sempre presente e pode ser `null`, o que indica que o catálogo não publicou nenhum. Nesse caso, execute `terms/show` primeiro e envie o digest retornado.

```json
{
  "status": "completed",
  "exchange": {
    "enabled": true,
    "onTermsRequired": "ask",
    "paidCalls": 0,
```

### Aceite e continue {#accept-then-continue}

No modo `ask`:

1. Mostre os termos ao usuário. Execute a chamada `show` do provider via [`/v2/scrape`](/pt-BR/features/alexandria) com `alexandria`.
2. Somente se o usuário concordar explicitamente, execute a chamada `accept` do provider da mesma forma. Se `accept.options.digest` for `null`, use o digest retornado por `terms/show`:

```bash
curl -X POST https://api.firecrawl.dev/v2/scrape \
  -H "Authorization: Bearer $FIRECRAWL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "alexandria": {
      "provider": "firecrawl",
      "capability": "terms/accept",
      "options": { "provider": "apollo", "version": "F-1.0.0", "digest": "<sha256>", "confirmed": true }
    }
  }'
```

3. Continue a mesma thread com `exchange.approve`. A oferta é aceita por completo, e `callIds` e `always` são ignorados nela. O próximo turno usa esses providers para preencher a lacuna indicada na resposta anterior, sem precisar executar tudo de novo.

```bash
curl -X POST https://api.firecrawl.dev/v2/agent \
  -H "Authorization: Bearer $FIRECRAWL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "threadId": "<threadId from the previous run>",
    "prompt": "Continue with Apollo.",
    "exchange": {
      "approve": { "approvalId": "0199aaaa-0000-7000-8000-000000000000" }
    }
  }'
```

Para prosseguir sem o provider, continue com `exchange.decline: { "approvalId": "..." }`. Isso recusa a oferta inteira, e os providers incluídos nela não serão oferecidos novamente no restante da thread.

No modo `skip`, não há aprovação pendente a ser respondida. Depois que os termos forem aceitos, inicie uma nova execução (ou um novo turno da thread) e o provider ficará disponível.

## Upload de CSV no Agent Playground {#csv-upload-in-agent-playground}

O [Agent Playground](https://www.firecrawl.dev/app/agent) oferece suporte a upload de CSV para processamento em lote. Seu CSV pode conter uma ou mais colunas de dados de entrada. Por exemplo, uma única coluna com nomes de empresas, ou múltiplas colunas como nome da empresa, produto e URL do site. Cada linha representa um item para o agente processar.

Envie seu arquivo CSV e, em seguida, adicione colunas de saída usando o botão &quot;+&quot; no cabeçalho da grade. Cada coluna tem seu próprio prompt — clique no cabeçalho de uma coluna para descrever o que o agente deve encontrar para esse campo (por exemplo, &quot;Nome do CEO ou fundador&quot;, &quot;Total captado em investimentos&quot;). Clique em Run, e o agente processa cada linha em paralelo, preenchendo os resultados.

## Preços {#pricing}

O Firecrawl Agent usa **cobrança dinâmica**, que acompanha a complexidade da sua solicitação de extração de dados. Você paga com base no trabalho efetivamente realizado pelo Agent, garantindo preços justos tanto ao extrair dados simples quanto informações estruturadas complexas de múltiplas fontes.

### Como funciona o preço do agente {#how-agent-pricing-works}

Os preços do agente são **dinâmicos e baseados em créditos**:

* **Extrações simples** (como informações de contato de uma única página) normalmente consomem menos créditos e custam menos
* **Tarefas de pesquisa complexas** (como análise de concorrência em vários domínios) consomem mais créditos, mas refletem o esforço total envolvido
* **Uso transparente** mostra exatamente quantos créditos cada requisição consumiu
* **Conversão de créditos** converte automaticamente o uso de créditos do agente em créditos para facilitar a cobrança

<Info>
  O uso de créditos varia de acordo com a complexidade do seu prompt, a quantidade de dados processados e a estrutura do resultado solicitado. Como orientação geral, a maioria das execuções do agente consome **algumas centenas de créditos**, embora tarefas simples em uma única página possam usar menos e pesquisas complexas em vários domínios possam usar mais.
</Info>

### Preços para Agentes em Paralelo {#parallel-agents-pricing}

Se você estiver executando vários agentes em paralelo com o Spark-2 Fast, o custo se torna muito mais previsível: 10 créditos por célula.

### Começando {#getting-started}

**Todos os usuários** recebem **5 execuções gratuitas por dia**, que podem ser usadas tanto no playground quanto na API, para explorar os recursos do Agent sem nenhum custo.

O uso adicional é cobrado com base no consumo de créditos e convertido em créditos.

### Gerenciando custos {#managing-costs}

agente pode ser caro, mas há algumas maneiras de reduzir o custo:

* **Comece com execuções gratuitas**: Use suas 5 requisições gratuitas diárias para entender os preços
* **Defina o parâmetro `maxCredits`**: Limite seus gastos definindo um número máximo de créditos que você está disposto a usar. O painel limita isso a 2.500 créditos; para definir um limite maior, use o parâmetro `maxCredits` diretamente via API (observação: valores acima de 2.500 são sempre cobrados como requisições pagas)
* **Otimize os prompts**: Prompts mais específicos geralmente usam menos créditos
* **Divida tarefas grandes em execuções menores**: Uma única execução do agente retorna aproximadamente 150-200 linhas de dados estruturados. Para jobs grandes de extração, divida por categoria, região ou lote de URLs (3-5 URLs por execução) e mescle os resultados. Isso também mantém cada execução bem abaixo do limite de `maxCredits`.
* **Monitore o uso**: Acompanhe seu consumo pelo painel
* **Ajuste expectativas**: Pesquisas complexas em múltiplos domínios vão consumir mais créditos do que extrações simples de uma única página

Teste o agente agora em [firecrawl.dev/app/agent](https://www.firecrawl.dev/app/agent) para ver como o uso de créditos escala com seus casos de uso específicos.
